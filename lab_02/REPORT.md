### 1 Имена и ссылки

В task_1.py проверены числа, списки и две конфигурации проекта.

Таблица 1 — Ожидания и результаты

| Действие | Ожидалось | Получено |
|---|---|---|
| a = 10; b = a | Один объект | Значения 10, id одинаковые |
| a += 1 | b не изменится | a = 11, b = 10, id разные |
| second = first; append(30) | Изменятся оба имени списка | Оба показывают [10, 20, 30] |
| second = list(first) | Равные, но разные списки | == True, is False |

До переназначения два имени ведут к одному списку. После копирования second ведет к другому списку.

```text
До:
first  ---+
          +--> [10, 20, 30]
second ---+

После second = list(first):
first  ------> [10, 20, 30]
second ------> [10, 20, 30]  другой список
```

Рисунок 1 — Связи имен со списками

Присваивание не меняет и не копирует объект. Оно связывает с ним еще одно имя. Число изменить нельзя, поэтому a += 1 связывает a с результатом 11, а b остается связанным с 10. Оператор is проверяет, один ли это объект; == сравнивает значения. Пока объекты существуют одновременно, одинаковые id означают один объект.

В конфигурациях название хранится строкой, участники — списком, параметры — вложенным списком. После deepcopy изменения вложенных списков независимы. Это проверено через assert.

Ответы на вопросы задания 1

Вопрос 1. Меняет ли присваивание second = first сам объект?
Ответ: нет. Список остается тем же, просто на него указывает еще одно имя second.

Вопрос 2. Почему операция над неизменяемым объектом связывает имя с другим объектом?
Ответ: само число изменить нельзя. Python вычисляет результат и связывает имя с ним. Поэтому после a += 1 имя a обозначает 11, а b по-прежнему обозначает 10.

Вопрос 3. Как определить, что два имени обозначают один объект?
Ответ: проверить a is b. Для одновременно существующих объектов их id тоже совпадут. Оператор == проверяет значения, а не идентичность.

### 2 Копирование вложенных списков

В task_2.py alias получен присваиванием, shallow — через copy(), deep — через deepcopy(). Сначала добавлена работа Databases с оценкой 5, затем первая оценка заменена на 3.

Таблица 2 — Оценки после изменений

| Структура | После append | После замены оценки |
|---|---|---|
| original | [5, 4, 5] | [3, 4, 5] |
| alias | [5, 4, 5] | [3, 4, 5] |
| shallow | [5, 4] | [3, 4] |
| deep | [5, 4] | [5, 4] |

Прогноз совпал с результатом: append виден у original и alias, замена вложенной оценки — еще и у shallow. Внешний id одинаков только у original и alias. Первая вложенная строка общая у original, alias и shallow. У deep она отдельная. До замены id числа 5 совпадал у всех: копировать неизменяемое число заново не нужно.

Таблица 3 — Сравнение копий

| Операция | Новый внешний объект | Новые вложенные списки | Изменения независимы |
|---|---|---|---|
| Присваивание | Нет | Нет | Нет |
| Поверхностная копия | Да | Нет | Только во внешнем списке |
| Глубокая копия | Да | Да | Да для этих данных |

В wrong_matrix = [[0] * 3] * 3 все строки — один объект. Поэтому замена первого элемента дала три строки [1,0,0]. В correct_matrix каждая строка создается отдельно через включение. Изменилась только первая строка. Выведенные id строк подтвердили прогноз.

Поверхностной копии достаточно, если меняется только внешний список или его элементы неизменяемы. Глубокая копия нужна для независимого изменения вложенных данных. Делать ее всегда не стоит: она занимает лишние время и память и подходит не для всех объектов.

Ответы на вопросы задания 2

Вопрос 1. Чем поверхностная копия отличается от глубокой?
Ответ: поверхностная копия создает новый внешний контейнер, но сохраняет ссылки на вложенные объекты. deepcopy копирует и вложенные изменяемые данные. Поэтому замена вложенной оценки видна в shallow, но не в deep.

Вопрос 2. Почему глубокое копирование не следует применять автоматически?
Ответ: оно требует дополнительной памяти и времени, даже если независимые вложенные данные не нужны. Кроме того, не все объекты можно так копировать, например открытый файл.

Вопрос 3. Когда достаточно поверхностной копии?
Ответ: когда меняется только внешний контейнер либо его элементы неизменяемы. Например, можно добавить число в копию списка чисел, не меняя исходный список.

### 3 Сильные и слабые ссылки

Таблица 4 — Счетчик ссылок на data

| Шаг | Ожидалось | Получено |
|---|---|---|
| Создание data | 2 | 2 |
| alias = data | 3 | 3 |
| container = [data] | 4 | 4 |
| del alias | 3 | 3 |
| container.clear() | 2 | 2 |

sys.getrefcount() добавляет временную ссылку на время вызова. Поэтому для одного имени получается 2. Присваивание alias и добавление в контейнер увеличивают счетчик; del alias и clear() уменьшают. del удаляет имя, а объект живет, пока на него есть сильные ссылки.

После del record слабая ссылка weak_record() вернула None, как и ожидалось. В WeakValueDictionary сначала были a, b, c; после del c остались a, b, после del a — только b. Слабый словарь не удерживает объекты. Это удобно, например, для кэша: он не мешает удалять ненужные данные.

Обычный объект CPython можно освободить, когда сильных ссылок не осталось. Для циклов нужен сборщик мусора. Освобожденная память может остаться у Python для повторного использования, а не сразу вернуться операционной системе.

Ответы на вопросы задания 3

Вопрос 1. Когда подсчет ссылок позволяет освободить объект?
Ответ: когда число сильных ссылок на обычный объект CPython становится равным нулю. Недоступные циклы отдельно ищет сборщик мусора.

Вопрос 2. Всегда ли освобождение объекта сразу возвращает память операционной системе?
Ответ: нет. Python может оставить освобожденный блок памяти для следующих объектов.

Вопрос 3. Чем сильная ссылка отличается от слабой?
Ответ: сильная ссылка удерживает объект в памяти, слабая — нет. После удаления последней сильной ссылки weakref возвращает None.

Дополнительный вопрос 1. Почему getrefcount показывает лишнюю ссылку?
Ответ: передача объекта в sys.getrefcount() временно добавляет ссылку на время вызова.

Дополнительный вопрос 2. Какие действия меняют счетчик?
Ответ: alias = data и container = [data] увеличивают его на один. del alias и container.clear() уменьшают на один.

Дополнительный вопрос 3. Почему del alias не удаляет объект напрямую?
Ответ: del убирает только имя alias. Если остались другие сильные ссылки, объект продолжает существовать.

Дополнительный вопрос 4. Где полезны слабые ссылки?
Ответ: в кэше объектов, который не должен мешать удалять данные после завершения работы с ними.

### 4 Циклы и сборщик мусора

Автоматическая сборка была включена. Выведены пороги (700,10,10) и статистика поколений. Во время опытов сборка отключалась, а finally снова включал ее через gc.enable().

Таблица 5 — Ручная сборка

| Опыт | Ожидалось | Получено gc.collect() |
|---|---|---|
| Два списка ссылаются друг на друга | Соберутся два списка | 2 |
| Пять списков ссылаются сами на себя | Соберутся пять списков | 5 |
| Перед созданием графа | Новых циклов нет | 0 |
| После удаления имен A, B, C | Соберутся три словаря и три списка | 6 |

У пары списков обе проверки first[0] is second и second[0] is first дали True. Их id сохранены до удаления имен. Сами числа id объекты не удерживают.

В графе каждый узел — словарь с name и списком edges. Связи добавлены через append.

```text
A.edges[0] --> B
B.edges[0] --> C
C.edges[0] --> A

independent --> D, edges = []
```

Рисунок 2 — Цикл и отдельный узел

После del a, b, c цикл стал недоступен, но его объекты продолжали ссылаться друг на друга. Поэтому одного подсчета ссылок недостаточно. gc.collect() нашел цикл. Узел D остался доступен, что проверено через assert.

Цикл получается, когда цепочка ссылок возвращается к исходному объекту. Счетчик может быть ненулевым из-за ссылок внутри такого недоступного цикла. Поколения нужны, чтобы чаще проверять новые объекты и реже — те, которые живут долго. Пороги и результаты сборки могут отличаться при другом запуске.

Ответы на вопросы задания 4

Вопрос 1. Как возникает циклическая ссылка?
Ответ: объект прямо или через другие объекты ссылается на себя. Например, first содержит second, а second содержит first.

Вопрос 2. Почему объект с ненулевым счетчиком может быть недостижим?
Ответ: на него могут ссылаться только другие объекты недоступного цикла. Из работающей программы к ним уже нельзя обратиться, хотя внутренние ссылки остались.

Вопрос 3. Зачем нужны поколения сборщика мусора?
Ответ: новые объекты часто быстро становятся ненужными. Их выгодно проверять чаще, а давно существующие объекты — реже. Это уменьшает затраты на сборку.

### 5 Память

В memory_report.py сначала все измерения сохраняются в rows и growth, затем печатаются. Для каждого сценария трассировка запускается и останавливается отдельно. 1 КиБ = 1024 байта.

Таблица 6 — Результаты измерений

| Сценарий | Элементы | Внешний размер, Б | Текущий, КиБ | Пиковый, КиБ |
|---|---|---|---|---|
| Пустой список | 0 | 56 | 0.055 | 0.055 |
| Список 10 чисел | 10 | 136 | 0.133 | 0.211 |
| Кортеж 10 чисел | 10 | 120 | 0.117 | 0.195 |
| Строка abcdefghij | 10 | 51 | 0.750 | 0.750 |
| Целое 1000 | 1 | 28 | 0.000 | 0.000 |
| None | 1 | 16 | 0.000 | 0.000 |
| list(range(100000)) | 100000 | 800056 | 3898.273 | 3898.383 |
| range(100000) | 100000 | 48 | 0.078 | 0.078 |

getsizeof() для списка включает его служебные данные и ссылки, но не полный размер элементов. tracemalloc показывает выделения во время опыта, в том числе служебные. Поэтому это другой показатель. Константы могут существовать еще до включения трассировки.

Прогноз подтвердился: list хранит все числа, а range — правило их получения. Пик для списка оказался в 49899.30 раза больше. Точные размеры зависят от запуска.

Таблица 7 — Рост списка при добавлении ста элементов

| Длина | Размер, Б | Длина | Размер, Б |
|---|---|---|---|
| 0 | 56 | 33 | 376 |
| 1 | 88 | 41 | 472 |
| 5 | 120 | 53 | 568 |
| 9 | 184 | 65 | 664 |
| 17 | 248 | 77 | 792 |
| 25 | 312 | 93 | 920 |

Размер менялся не после каждого append, как и ожидалось. Список заранее выделяет места для следующих ссылок, чтобы реже увеличивать память. Длина — число элементов, а выделенный объем может включать запас.

Память можно экономить так: использовать range вместо большого списка (задание 5); делать поверхностную копию, если вложенные данные менять не нужно (задание 2); удалять ненужные сильные ссылки или применять слабый кэш (задание 3).

Ответы на вопросы задания 5

Вопрос 1. Почему размер контейнера не включает полный размер его элементов?
Ответ: контейнер хранит ссылки. sys.getsizeof() измеряет сам контейнер, а объекты по его ссылкам отдельно не обходит.

Вопрос 2. Растет ли размер списка после каждого append?
Ответ: нет. В опыте размер менялся только на отдельных шагах, например при длине 1, 5 и 9.

Вопрос 3. Почему список выделяет память с запасом?
Ответ: чтобы не выделять новый блок при каждом добавлении элемента. Следующие append используют свободные места.

Вопрос 4. Чем длина списка отличается от выделенного объема памяти?
Ответ: длина — число уже добавленных элементов. В выделенной памяти также есть служебные данные и запас мест для ссылок.

Вопрос 5. Почему list(range(100000)) занимает больше памяти, чем range(100000)?
Ответ: список хранит ссылки на все числа, а range хранит начало, конец и шаг. Числа из range получаются по мере обхода.

Вопрос 6. Как уменьшить лишнее потребление памяти?
Ответ: использовать range вместо большого списка, когда нужен обход; не делать deepcopy без необходимости; удалять ненужные сильные ссылки или использовать слабый кэш.
